## Summary

A **shape addition.** v0.5 mandated git on the Payload — clean for code projects whose Payload *is* what ships, awkward for projects whose deliverable is a folder elsewhere (a Drive folder, a static site, a client directory). v0.5.1 introduces an optional second project shape: the Payload moves into a `payload/` folder paired with a `publish/` sibling that carries the curated deliverable. A new verb, [`publish`](../verbs/publish.md), syncs `payload/` → `publish/` per a project-specific recipe in `blueprint/processes/publish.process.md`. The split also creates a deliberate curation gate — the recipe decides what crosses from workshop to deliverable.

The organising principle: *the Payload is where the work happens; what ships is downstream of it.*

## Changes

**New term — Publish.** A sixth term joins Project / Payload / Lore / Memory / References. **Publish** is an optional curated destination derived from the Payload — the deliverable for projects whose ship target is not the Payload itself. Lives at `<project>/publish/`, paired with `<project>/payload/`. May be a real directory or a symlink to an external mount (Drive folder, static-site source, deploy directory). Excluded from both git repos — derived state, regenerable from `payload/` at any time.

**Payload becomes shape-dependent.** By default (the v0.5 shape, unchanged) the Payload occupies the project root directly. In Publishing projects, the Payload lives in its own `payload/` folder at the project root — sibling to `publish/`, the Lore folder, and the shim. The change is opt-in: projects that don't declare Publishing are unaffected.

**New verb — `publish`.** Syncs the contents of `payload/` (the curated subset) into `publish/` per the project's `blueprint/processes/publish.process.md` recipe. Refuses on projects whose `workspace.yaml` carries no `publish:` block. Refuses when the recipe does not exist. One-way (`payload/` → `publish/`); never the reverse. The session does not self-publish — invocation is the Human Lead's call because publishing is visible outward.

**Write-discipline rule.** A session in `execute` posture may write to the Payload (the project root by default, `payload/` in Publishing), but **not** to `publish/`. Writes to `publish/` outside the `publish` verb are refused regardless of posture. This keeps the curation gate honest — `publish/` is downstream of the recipe, not a place sessions edit in place.

**`workspace.yaml` gets an optional `publish:` block.** Presence declares the project as a Publishing project; absence means the default shape (unchanged from v0.5). The block carries `path` (where `publish/` lives, defaults to `./publish`) and optional `target` (a symlink target; `init` creates the symlink when set).

**`init` branches on project shape.** A new step early in `init` asks whether the project is Publishing. Publishing projects get the `publish:` block in `workspace.yaml`, an empty `payload/` folder, the `publish/` directory or symlink, and a `publish/` entry in the Payload's `.gitignore` (the `publish/` ignore line is harmless on default-shape projects, also added there for forward compatibility).

**Verbs index — fifth group.** A new group joins Posture / Ack / Ordinary work / Lifecycle: **Outward** — `publish`. Sync the curated subset of the Payload to the external deliverable. Publishing projects only.

**Naming explicitly rejected.** "Mirror" was the natural-sounding name and was rejected — it collides with `blueprint/mirror/` (the description of the Payload's shape). `publish/` was chosen because it travels: works for Drive folders, static sites, deploy targets, any "publish to X" destination, and pairs cleanly with a verb of the same name.

## Migration

Ships with [`migration-from-v0.5.md`](../migration-from-v0.5.md) at the methodology root, applied by the [`upgrade`](../verbs/upgrade.md) verb.

The playbook is short by design — v0.5.1 is additive, so the **required** path is just two steps: re-place the methodology, bump `core_version` to `0.5.1`. Every v0.5 project runs that path and is done.

The playbook then branches into an **optional publishing-shape adoption** — six steps for projects whose deliverable is a folder elsewhere. The structural step is moving existing Payload contents into a new `payload/` folder via `git mv` (preserves history); the remaining steps create `publish/`, update `.gitignore`, add the `publish:` block to `workspace.yaml`, and author `<lore>/memory/blueprint/processes/publish.process.md` (the project-specific recipe). The branch is opt-in — projects whose deliverable IS the Payload skip it entirely.
